Why it didn't fire

If your Skill from L01 sat there doing nothing, one field is almost certainly why. You're going to break yours on purpose, watch it fail, then fix it — because a Skill you can repair is worth more than one that happened to work.

~12 min Needs your L01 Skill No files, no terminal
Readone screen

Claude is choosing blind

Remember from L01: Claude does not read your Skills when deciding. It sees only their names and one-line descriptions, and opens the full instructions for whichever description matches what you just asked. ¹

So the description is not a summary for humans. It is the trigger. Beautiful instructions behind a vague description are unreachable — which is exactly what happened if yours stayed silent.

A description needs two halves: what it does + when to use it.
Miss the second half and it will not fire.

Won't fire

description: Helps with documents

Anthropic's own example of what not to write. Nothing here matches anything you'd actually type. ¹

Will fire

description: Analyze Excel spreadsheets, create pivot tables, generate charts. Use when analyzing Excel files, spreadsheets, tabular data, or .xlsx files.

Says what it does, then names the words a person would really use — including the file extension.

third person

Write "Formats client decks…", never "I can help you format decks…" or "You can use this to…". The description gets injected into Claude's own instructions, and a mixed point of view measurably hurts discovery. ¹ This is the single most common mistake after vagueness.

There is a second, duller reason a Skill goes silent: it is switched off. Before you debug anything, check Settings → Customize → Skills and confirm yours is actually enabled.
Dobreak it first

Break it, then fix it

Why break something that works

Because you'll meet this failure again in six months, on a Skill you didn't write, with no memory of this lesson. Watching the failure happen on purpose — while you know the cause — is what makes it recognisable later. Skip this and you'll only have read about it.

  1. Look at your description

    Open your L01 Skill and find its description. Read it against one question: does it contain the words I'd actually type when I want this?

    If your Skill is about client decks but the description says "assists with presentation preparation", the mismatch is right there. You'd type "deck", it says "presentation preparation".

  2. Break it deliberately

    Change the description to exactly this, and save:

    Helps with documents

    Now open a new conversation and ask for your task the normal way. It should be ignored. Confirm the failure — that's the point of the step.

  3. Rebuild it with the formula

    Write it in two halves. Sentence one, what it does. Sentence two, starting with "Use when", naming the words you actually say — and paste in the real phrasing you used in step 2's test.

    Formats weekly client status decks in the house
structure. Use when the user mentions a client deck,
a status deck, a weekly update slide, or asks to
build or restructure a PowerPoint for a client.

    Notice it lists four ways of asking for the same thing. That redundancy is not clutter — it's the whole mechanism.

  4. Test in a new conversation

    New chat, ask naturally, don't name the Skill. If it fires, you've just done the full debug loop yourself.

    Still silent? Ask Claude directly: "I have a Skill with this description. Why wouldn't it trigger when I ask for a client deck?" Paste both. Claude can read its own selection logic and will usually tell you exactly what's missing — that's a debugging move worth keeping.

  5. One extra sentence, for later

    Add the words a colleague would use, not just yours. If you say "deck" and your team says "the weekly pack", put both in. You'll need this in L04, when someone else runs your Skill and it ignores them.

What must a description contain to work at all?

Both halves. "What it does" alone is the classic silent Skill — Claude has no way to tell whether your request is an occasion for it. "Use when…" is the half people forget.

Which point of view should a description use?

Third person. The description is injected into Claude's own instructions, so "I can help you…" and "You can use this to…" both read as noise from the wrong speaker and hurt discovery.

Your Skill ignores the exact phrase you always type. Best fix?

The description — that's the only part Claude reads before choosing. Adding them to the instructions changes nothing, because the instructions are never opened unless the description won first. This distinction is the whole lesson.
